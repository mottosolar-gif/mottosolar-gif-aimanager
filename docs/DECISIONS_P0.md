# คำตัดสินของผู้ออกแบบ — P0 (มีผลเหนือใบสั่งงานเดิมเมื่อขัดกัน)

## D-P0-01 · `inbox_event` เก็บ metadata เท่านั้น ห้ามเก็บเนื้อความ
2026-08-27 · เกิดจาก Codex ทักว่า WP-P0-3 ("เก็บ event ดิบ") ขัดกับกฎห้ามข้อมูลบุคคลขึ้นคลาวด์ — **Codex ทักถูก**

**เก็บได้:**
- `event_id` (LINE `webhookEventId`) UNIQUE — กุญแจกันซ้ำ
- `event_type` (message / postback / join / leave / follow …)
- `message_type` (text / image / audio / location / sticker …) — ชนิดเท่านั้น
- `source_type` (user / group / room)
- `source_hash` — SHA-256 ของ userId/groupId + salt จาก env · **ห้ามเก็บ id ดิบ**
- `occurred_at` — เวลาที่เหตุการณ์เกิดจริง (จาก LINE timestamp)
- `received_at` — เวลาที่คลาวด์รับเข้ามา
- `payload_bytes` (INTEGER) · `payload_sha256` — พิสูจน์ว่าได้รับอะไรมาโดยไม่ต้องเก็บของจริง
- `status` · `attempts` · `last_error` (error ของระบบเท่านั้น)
- `body_ref` (TEXT NULL) — ช่องไว้ชี้ที่เก็บเนื้อความภายนอกในอนาคต · **เฟสนี้ต้องเป็น NULL เสมอ**

**ห้ามเก็บเด็ดขาด:** ข้อความที่ผู้ใช้พิมพ์ · ชื่อ/นามสกุล/ชื่อแสดงผล · เบอร์โทร · อีเมล · เหตุผลการลา · URL รูปที่ดาวน์โหลดได้ · LINE id ดิบ

**เหตุผล:** P0 มีเป้าหมายเดียว — พิสูจน์ว่าท่อทะลุและกันซ้ำได้ ซึ่ง metadata เพียงพอ
เนื้อความจะถูกอ่านโดยชั้นสมองที่รันบนเครื่องภายใน (homelab) ในเฟสถัดไป **ไม่เก็บถาวรบนคลาวด์**

**ยาม privacy ต้องตรวจ 3 อย่าง:**
1. schema ไม่มีคอลัมน์ต้องห้าม (`name` `fullname` `phone` `email` `reason` `text` `message`)
2. `body_ref` เป็น NULL ทุกแถว
3. ไม่มีค่าที่หน้าตาเป็น LINE id ดิบ (`^U[0-9a-f]{32}$` / `^C[0-9a-f]{32}$`) อยู่ในฐาน

**เทสบังคับเพิ่ม:** ยิง event ที่มีข้อความยาว → ตรวจว่าข้อความนั้นไม่ปรากฏที่ใดในฐานเลย

## D-P0-02 · ⛔ ห้ามแตะ Worker `mottosolar-line-relay`
2026-08-27 · ตรวจจากหน้า Cloudflare จริงของเจ้าของ

Worker ชื่อนี้มีอยู่แล้วในบัญชีเดียวกัน และ **ทำงานจริง 22,370 invocations ใน 24 ชม.** (~15 ครั้ง/นาที · Errors 0 · binding = Durable Object `QUEUE`)
เป็นของระบบ **homelab** ที่รับ LINE webhook ไปพักไว้ให้ปลายทางดึง — ถ้า deploy ทับ ระบบนั้นตายทันที

⇒ **Worker ของโครงการนี้ต้องชื่อ `aim-ingest`**
⇒ `wrangler.toml` อ่าน `account_id` จาก environment (`CLOUDFLARE_ACCOUNT_ID`) ห้ามฝังในไฟล์

**โควตาที่ต้องเคารพ:** แพลนฟรีให้ 100,000 invocations/วัน **ต่อบัญชี** และตัวเดิมใช้ไปแล้ว ~22%
⇒ ห้ามออกแบบให้ poll ถี่ · Cron ทุก 1 นาที = ~1,440 ครั้ง/วัน ถือว่าเหมาะสม

## D-P0-05 · ผลตรวจ code-reviewer อิสระ (2026-08-27) — สรุปและติดตามผล

**ผ่าน** สำหรับขอบเขต WP-P0-1..3 — ไม่พบช่องโหว่ PII ที่ใช้ประโยชน์ได้จริงในโค้ดปัจจุบัน, constant-time comparison ถูกต้อง, idempotency ทนต่อ concurrent request จริง, secrets ไม่หลุดเข้า git

**MEDIUM ที่สั่งแก้แล้ว (round 7):** `schema/privacy-guard.mjs` เป็น denylist ชื่อคอลัมน์ — พิสูจน์แล้วว่าหลบเลี่ยงได้ด้วยชื่อคอลัมน์คำพ้องความหมาย (`note` ไม่อยู่ใน denylist) ⇒ เปลี่ยนเป็น allowlist ตายตัวต่อคอลัมน์ต่อตาราง (ดู `ALLOWED_COLUMNS` ใน round 7 instructions)

**LOW ที่สั่งแก้พร้อมกัน:** เพดานจำนวน event ต่อ request (defense-in-depth) · ผูก `privacy:check:remote` เข้า CI post-deploy (ตอนนี้เป็นแค่การรันมือ)

**บันทึกไว้เป็น backlog ไม่บล็อก P0 (ยังไม่ต้องแก้ตอนนี้):**
- `job_queue.idem_key` ใช้แค่ `event.eventId` เดี่ยว ๆ — พอสำหรับ P0 ที่มี kind เดียว ถ้าเฟสหน้ามีมากกว่า 1 job ต่อ event ต้องทบทวนคีย์ให้รวม `kind` ด้วย
- `extractMetadata` ใช้ `Promise.all` ครอบทุก event ในชุดเดียว ⇒ event เดียวผิดรูปทำให้ทั้งชุดถูกปฏิเสธ 400 หมด — ไม่ใช่ปัญหา privacy (ไม่มีอะไรถูกเก็บทั้งสองกรณี) แต่เป็นความเสี่ยง completeness ที่ต้องคิดตอนออกแบบ WP-P0-4/5 (ระบบเดิม cim-server ทนได้เพราะ fail แล้วเดินหน้าต่อ แต่ AI Manager จะเสีย event นั้นไปเงียบ ๆ ถ้าไม่ทำ retry แยกราย event)

## D-P0-06 · ⛔ ถอดเครื่องมือ `schema/privacy-guard.mjs` ออกทั้งหมด (2026-08-27 — เจ้าของระบบตัดสินเอง)

**บริบท:** เจ้าของระบบชี้ว่าชื่อในกลุ่ม LINE เป้าหมายเป็นชื่อเล่น/ชื่อปลอมทั้งหมด ไม่ใช่ชื่อจริง
ผู้ออกแบบ (Claude) ชี้แจงก่อนว่ายามนี้ไม่เคยแตะ display name เลยตั้งแต่แรก (VERIFIED จากโค้ด — grep ทั้ง repo ไม่เจอ)
สิ่งที่ยามป้องกันจริงคือ (1) LINE `userId` ดิบ ซึ่งเป็นรหัสถาวรผูกกับบัญชีจริงไม่ว่าจะตั้งชื่อโชว์เป็นอะไร
และ (2) เนื้อความที่พิมพ์ซึ่งอาจมีชื่อจริง/เบอร์โทร/เหตุผลลาได้เสมอไม่เกี่ยวกับชื่อโชว์ของผู้พิมพ์
เสนอ 3 ทางเลือก (คง denylist→allowlist เดิม / เก็บ userId ดิบไม่ hash / ถอดยามอัตโนมัติทั้งชุด) — **เจ้าของระบบเลือกทางที่ 3**

**ผลของคำตัดสิน:**
- ลบ `schema/privacy-guard.mjs` และการเรียกใช้ทั้งหมด (`npm run privacy:check` / `:local` / `:remote`,
  step ใน `.github/workflows/deploy.yml` ทั้งใน job `test` และ `deploy`)
- **ไม่กระทบกลไกอื่นที่แยกกันโดยสิ้นเชิง** — ยังคงอยู่เหมือนเดิมทุกจุด:
  - `hashSourceId()` ใน `crypto.ts` ยังแฮช LINE userId/groupId ก่อนเก็บทุกครั้ง (ไม่ได้ยกเลิกการ hash)
  - `body_ref TEXT CHECK (body_ref IS NULL)` ยัง enforce ที่ระดับฐานข้อมูลเหมือนเดิม
  - `schema/check-migration.mjs` ยังทดสอบ constraint เหมือนเดิม (คนละเครื่องมือกับที่ถอดออก)

**ผลกระทบที่ต้องรู้ไปข้างหน้า:** จากนี้ migration ใหม่จะเพิ่มคอลัมน์ชื่อ/เบอร์/ข้อความ/เหตุผลลาได้โดย **ไม่มีระบบอัตโนมัติเตือน** —
เป็นการตัดสินใจรับความเสี่ยงของเจ้าของระบบเอง (ทางเลือกที่ 1/2 เคยเสนอไว้เป็นทางที่คุมความเสี่ยงมากกว่าแต่ไม่ถูกเลือก)
คนที่รีวิว migration ใหม่ในอนาคตต้องตรวจคอลัมน์ที่เพิ่มด้วยตาเองแทน — บันทึกไว้เป็นความรู้สำหรับผู้ตรวจรอบถัดไป (Claude/code-reviewer)
ให้ยกเรื่องนี้ขึ้นมาตรวจด้วยตาทุกครั้งที่มี migration ใหม่ตั้งแต่นี้ไป
