## D-P0-01 · `inbox_event` เก็บ metadata เท่านั้น ห้ามเก็บเนื้อความ
2026-08-27 · เกิดจาก Codex ทักว่า WP-P0-3 ("เก็บ event ดิบ") ขัดกับกฎห้ามข้อมูลบุคคลขึ้นคลาวด์ — **Codex ทักถูก**

**เก็บได้:**
- `event_id` (LINE `webhookEventId`) UNIQUE — กุญแจกันซ้ำ
- `event_type` (message / postback / join / leave / follow …)
- `message_type` (text / image / audio / location / sticker …) — ชนิดเท่านั้น
- `source_type` (user / group / room)
- `source_hash` — SHA-256 ของ userId/groupId + salt จาก env · **ห้ามเก็บ id ดิบ**
- `occurred_at` — เวลาที่เหตุการณ์เกิดจริง (จาก LINE timestamp)
- `received_at` — เวลาที่คลาวด์รับเข้ามา
- `payload_bytes` (INTEGER) · `payload_sha256` — พิสูจน์ว่าได้รับอะไรมาโดยไม่ต้องเก็บของจริง
- `status` · `attempts` · `last_error` (error ของระบบเท่านั้น)
- `body_ref` (TEXT NULL) — ช่องไว้ชี้ที่เก็บเนื้อความภายนอกในอนาคต · **เฟสนี้ต้องเป็น NULL เสมอ**

**ห้ามเก็บเด็ดขาด:** ข้อความที่ผู้ใช้พิมพ์ · ชื่อ/นามสกุล/ชื่อแสดงผล · เบอร์โทร · อีเมล · เหตุผลการลา · URL รูปที่ดาวน์โหลดได้ · LINE id ดิบ

**เหตุผล:** P0 มีเป้าหมายเดียว — พิสูจน์ว่าท่อทะลุและกันซ้ำได้ ซึ่ง metadata เพียงพอ
เนื้อความจะถูกอ่านโดยชั้นสมองที่รันบนเครื่องภายใน (homelab) ในเฟสถัดไป **ไม่เก็บถาวรบนคลาวด์**

**ยาม privacy ต้องตรวจ 3 อย่าง:**
1. schema ไม่มีคอลัมน์ต้องห้าม (`name` `fullname` `phone` `email` `reason` `text` `message`)
2. `body_ref` เป็น NULL ทุกแถว
3. ไม่มีค่าที่หน้าตาเป็น LINE id ดิบ (`^U[0-9a-f]{32}$` / `^C[0-9a-f]{32}$`) อยู่ในฐาน

**เทสบังคับเพิ่ม:** ยิง event ที่มีข้อความยาว → ตรวจว่าข้อความนั้นไม่ปรากฏที่ใดในฐานเลย

## D-P0-07 · ผลตรวจ code-reviewer รอบ P0-5 (ติดตั้งจริงบน LIVE) — 2026-08-27

**ผ่าน — ปลอดภัยที่จะรันต่อบน production** ไม่พบ finding ระดับ Critical/High จากการอ่านโค้ดของ
`lib/aim_forward.php`, `config/aim.credentials.php`, และ 2 จุดที่แทรกใน `api/line_webhook.php`
ยืนยันเพิ่มเติมจากที่ Claude ทดสอบรันจริงไว้ก่อนหน้า: timeout ครอบคลุมถึงเฟส DNS จริง (ตรวจ `curl_version()`
บนเครื่อง — libcurl มี `CURL_VERSION_ASYNCHDNS`), ไม่มีทาง `'' === ''` หลุดกรองกลุ่มทดสอบผิด (กันสองชั้น),
ไม่ log เนื้อหาผู้ใช้เลย, จุดแทรกไม่กระทบโค้ดเดิมแม้แต่บรรทัดเดียว

**M1 — บันทึกเป็นข้อจำกัดที่รู้แล้ว (ไม่บล็อก ไม่แก้ตอนนี้):**
`aim_forward_events($events)` เรียกครั้งเดียวต่อ 1 คำขอ webhook (ทั้งก้อน) ก่อนเข้า foreach — LINE
สามารถส่งหลาย event จากหลายกลุ่ม/หลายคนมาในคำขอเดียวกันได้ถ้าเกิดใกล้เคียงกัน ถ้า event ของกลุ่มทดสอบ
มากับ event ของพนักงานจริงในคำขอเดียวกัน พนักงานจริงคนนั้นจะโดนหน่วงไปด้วย (สูงสุด ~1.5 วิ กรณีคลาวด์ล่ม)
⇒ **เหตุผลที่ยอมรับความเสี่ยงนี้ใน P0:** ปริมาณข้อความของกลุ่มทดสอบต่ำมาก โอกาสชนกันในคำขอเดียวกันต่ำ
และเพดานความล่าช้าจริงคือ 1.5 วิ ซึ่งยังไกลจาก `set_time_limit(280)` ของระบบมาก
⇒ **ทางแก้ที่ถูกต้องสำหรับเฟสถัดไป (ถ้าปริมาณโตขึ้น):** เปลี่ยนเป็นเขียนคิวท้องถิ่น (ตาราง/ไฟล์) แล้วให้
cron แยกยิงออกไป แทนการยิง HTTP ตรงในเส้นทาง webhook เอง — ตัดการพึ่งพา latency ของคลาวด์ออกจาก
เส้นทางหลักไปเลย ไม่ใช่แค่จำกัด timeout

**M2 — ต้องสร้างก่อนปิด WP-P0-5 (ตามที่สเปกตัวเองกำหนดไว้):** ยังไม่มี `bin/smoke_aim_forward.php`
ถาวรที่จับ regression ได้ถ้าอนาคตมีคนแก้ไฟล์นี้แล้วเผลอถอด try/catch หรือขยาย timeout โดยไม่รู้ตัว
— ผู้ตรวจก่อนหน้ามีแค่การทดสอบมือครั้งเดียว ไม่ใช่ยามถาวร → ดำเนินการสร้างต่อทันที (ดูหัวข้อถัดไป)

## D-P0-08 · บั๊กจริงจากการใช้งานจริงวันแรก — `webhookEventId` ของ LINE ขึ้นต้นด้วยตัวเลขถูกปฏิเสธทุกครั้ง

**2026-08-27 — เจอจาก log จริง ไม่ใช่ทดสอบ:** พี่เต้พิมพ์ข้อความในกลุ่มทดสอบ 2 ครั้ง ระบบยิงไปคลาวด์สำเร็จ
(fan-out ทำงานถูกต้องตามสเปค) แต่คลาวด์ตอบ `HTTP 400` ทุกครั้ง

**สาเหตุ:** `worker/src/payload.ts` `requiredToken()` บังคับตัวอักษรตัวแรกของ `webhookEventId` ต้องเป็น
`A-Za-z` แต่ ID จริงของ LINE เป็นรูปแบบ ULID ที่เข้ารหัส timestamp เป็นอักขระตัวแรก ⇒ **มักขึ้นต้นด้วยตัวเลข**
⇒ event จริงแทบทุกตัวถูกปฏิเสธ ตั้งแต่วันแรกที่ deploy โดยไม่มีใครรู้ เพราะทุกรอบทดสอบก่อนหน้า (ทั้งของ Codex
และของผู้ตรวจ) ใช้ค่าจำลองที่ตั้งขึ้นเอง (`test-evt-001`, `php-runtime-test-...`) ซึ่งบังเอิญขึ้นต้นด้วยตัวอักษร
เสมอ — **นี่คือกับดักเดียวกับบทเรียนเลข B/L ในกติกาบ้าน: ค่าจำลองที่ผู้ทดสอบเลือกเองมักผ่านกฎที่ผู้ทดสอบ

**แก้แล้ว:** regex เป็น `^[A-Za-z0-9][A-Za-z0-9_-]{0,127}$` (อนุญาตตัวเลขนำหน้า) · เพิ่มเทสด้วยค่ารูปแบบ ULID
จริง · deploy แล้ว (Version `df4dbf15`) · ยืนยันด้วย curl ตรงว่า payload เดิมที่เคยล้มเหลวตอนนี้ผ่านแล้ว (HTTP 200)

**บทเรียนสำหรับ P0-6/เฟสถัดไป:** เทสที่ auto-generate ค่าจำลองเองต้องสุ่มให้ครอบคลุมรูปแบบขอบเขตจริงด้วย
(เช่น ขึ้นต้นด้วยตัวเลข/ตัวอักษรสลับกัน) ไม่ใช่ยึดรูปแบบเดียวที่สะดวกกับผู้เขียนเทส
