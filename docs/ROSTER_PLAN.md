## สรุปหนึ่งย่อหน้า

สร้าง **Employee Registry** เป็นเจ้าของความจริงหนึ่งเดียวของ "ใครเป็นพนักงาน · สถานะ · สิทธิ์รายฟีเจอร์"
ฐานข้อมูลอยู่เครื่อง homelab · บริหารผ่าน LINE (การ์ดยืนยัน) + เว็บหน้าเดียว · ทุกระบบเดิม
(vendor-ksk / FIM / Cloudflare) ถือ**สำเนารู้อายุ** ที่ registry ป้อนให้อัตโนมัติ ·
**พนักงานไม่ต้องทำอะไรเลยและไม่รู้ว่ามีการเปลี่ยนแปลง** — FIM ลดบทบาทเหลือเจ้าของ
"รหัสผ่านเว็บของตัวเอง" เท่านั้น

## หลักการที่ล็อกไว้ (จากคำตัดสินเดิม — ไม่เปิดเถียงใหม่)

1. เดิน **Mirror → Dual-run 7 วัน → สลับเจ้าของ → ตัดของเก่า** (D-2026-08-29-ก) — ห้ามข้ามขั้น
2. **ขั้นแรกของ migration = พาค่าเดิมของทุกคนเข้าระบบใหม่ ก่อนปลดของเก่า** (บทเรียน Can_Leave)
3. ชื่อจริง/ข้อมูลบุคคล**ห้ามขึ้น Cloudflare** — คลาวด์เห็นแค่ `person_code` + สถานะ + สิทธิ์ (D-P0-01)
4. **ไม่แตะ credential เว็บ** — รหัสผ่านอยู่ db_fim ต่อ (H6) · registry เป็นเจ้าของ "การจ้างงาน" ไม่ใช่ "รหัส"
5. บอทเสนอ · คนยืนยัน · ระบบจำ — ทุกการเปลี่ยนสถานะต้องมีคนกด (AI ห้ามเขียนเอง)
6. ห้าม ENUM ฝั่ง MySQL (sql_mode ว่าง) · สคริปต์ฝั่ง homelab = ASCII + อ่านกุญแจจาก .env (กัน classifier)
7. สัญญาเสิร์ฟตัวเองที่ `?doc=` ห้ามมีสำเนา · `ref` UNIQUE กันซ้ำ · ส่ง full-set ไม่ทำ incremental
8. ผู้รับแจ้งเตือนสำคัญ = ไดนามิก `Is_Manager` ห้ามกริดติ๊ก

## เฟส R2 · Dual-run (ของเดิมยังเป็นเจ้าของ · registry วิ่งตาม)

- ทุกการเปลี่ยนในระบบเดิม (ปุ่มหน้า 8.1 FIM · users.php · sync) ต้องสะท้อนเข้า registry
  — ช่วงนี้ใช้ **full sync ตามรอบ** (ฝั่งเราส่งทั้งชุดให้ registry ทุก N ชม. — เจ้าของยังเป็นของเดิม
  จึงไม่มีเส้นทางเขียนสองทาง)
- `ksk-roster-reconcile` รายคืน + streak — **ประตู: ตรงกัน 100% ติดกัน 7 วัน** (เกณฑ์เดียวกับ P4)
- ระหว่างนี้ Codex สร้างของฝั่งผู้ใช้ล่วงหน้า (ยังไม่เปิด): ตัวรับ event → เขียน cache + หน้าบริหาร + การ์ด LINE

## เฟส R3 · สลับเจ้าของ (คำตัดสินเฉพาะ + rollback ที่เทสแล้ว)

1. **พี่เต้เคาะวันสลับ** (คำตัดสินรายระบบตาม D-2026-08-29-ก ขั้น 3)
2. เปิดทางเขียนใหม่: การ์ด LINE + เว็บหน้าเดียว → เขียน registry → event push ทันทีถึง:
   - vendor-ksk: อัปเดต `db_customs.tbl_user.user_status` + flags + revoke `tbl_line_user` — **LINE bot อ่านที่เดิม โค้ด webhook ไม่ต้องแก้**
   - FIM: ตั้ง `db_fim.tbl_user.user_status` (ตัด credential เว็บ) — ผ่าน endpoint เดิมที่ FIM มี หรือ full-sync
   - Cloudflare: provision/ระงับ `person`/`person_link` (แก้หนี้ D-P0-14 ในตัว)
3. ปิดทางเขียนเก่า (ปุ่ม dual-write หน้า 8.1 → เรียก registry แทน)
4. **Rollback ที่ต้องเทสก่อนวันจริง:** สวิตช์เดียวสลับกลับให้หน้าเดิมเขียนได้ + registry กลับเป็นผู้ตาม
5. fail-safe บังคับ: registry เงียบ ⇒ ทุกระบบใช้ cache ล่าสุดต่อ **ห้ามเตะใครออก ห้ามรับใครเพิ่ม** ·
   ยามอายุ cache แจ้ง `Is_Manager` เมื่อเกิน 6 ชม. (เกาะ `bridge_watchdog` เดิม — ห้ามงอกยามตัวที่ 7)

**ประตู R3:** ทดสอบครบวงจรกับบัญชี TEST (เพิ่ม/ปิด/เปิด/เปลี่ยนสิทธิ์ → ผลถึงครบ 3 ปลายทาง + rollback จริง 1 รอบ) · ทุก smoke เดิมผ่าน · จำนวนเทสไม่ลด

## เฟส R4 · ตัดของเก่า + เฝ้าดู

- ยาม "ของเก่าหยุดจริง": ไม่มีการเขียน `user_status` นอก pipeline (ตรวจจาก log/audit ไม่ใช่ grep)
- ปลด `sync_fim_users.php` + โค้ด dual-write เก่า — **คนละรอบกับ R3** (ห้ามลบในรอบเดียวกับที่ย้าย)
- อัปเดต CLAUDE.md ทุกฝั่ง + MEMORY ให้ชี้ความจริงใหม่

## สัญญา Registry v1 (โครงที่จะเขียนเต็มใน R0-2)

**ข้อมูลที่ registry ถือ (ต่อคน):** `person_code` (กุญแจถาวร — ใช้ตัวเดียวกับ aim) · ชื่อจริง/ชื่อเล่น ·
สถานะจ้างงาน (`active`/`left` — VARCHAR) · แผนก · สิทธิ์รายฟีเจอร์ (tool/leave/attend/manager) ·
`fim_user_id` + `customs_user_id` (กุญแจ map กลับ) · LINE binding hash · ประวัติการเปลี่ยน (ใครกด เมื่อไร)

**Endpoint หลัก:** `GET /roster` (full set + `as_of` timestamp) · `POST /roster/change` (idempotent `ref`) ·
`GET /healthz` · event push → ฝั่งเรารับที่ endpoint ใหม่ข้าง `bridge_intake` (โครงเดียวกัน — IIS binding
tailnet + กุญแจแยกดวง)

**หลักความจริง:** registry เป็นเจ้าของ "การจ้างงาน+สิทธิ์" · FIM เป็นเจ้าของ "รหัสผ่านเว็บ" ·
`tbl_line_user` ฝั่งนี้กลายเป็น cache ที่ registry ป้อน · คลาวด์เห็นเฉพาะ pseudonym
