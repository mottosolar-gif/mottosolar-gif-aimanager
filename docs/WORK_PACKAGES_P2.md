# ใบสั่งงาน P2 — สายตา + ปาก (อ่านข้อมูลจริง + ตอบคำถาม + สรุปเช้า-เย็น)

เขียน 2026-08-27 · ต่อจาก P1 (WP-P1-B ปิดจบสมบูรณ์ 100%, verified end-to-end จริง — D-P0-12)
พี่เต้อนุมัติเดินหน้าทั้ง P2-P5 รวด ("ไล่ไปเลย P2-5") — เอกสารนี้แตกเฉพาะ P2 ก่อน เพราะ P3 ขึ้นกับผล P2,
P4 ต้องรอ P2+P3 เสร็จก่อนถึงเริ่มนับเวลา ≥2 สัปดาห์ได้, P5 ต้องรอ P4 ผ่านเกท — ไล่ตามลำดับจริง ไม่ข้ามประตู

## เป้าหมาย (ตาม IMPLEMENTATION_PLAN.md §6)
read model + ตอบคำถามจากข้อมูลจริง + สรุปเช้า-เย็น + สิทธิ์การมองเห็นรายคน
**ประตู:** 20 คำถามมาตรฐาน ไม่มีคำตอบไหนแต่งขึ้น · ลูกน้องถามงานคนอื่นต้องไม่เห็น

## 0. จุดตัดสินสถาปัตยกรรมที่ต้องเคาะก่อนเริ่ม (เสนอ + เหตุผล — ไม่ใช่เดา)

**เสนอ: ตอบคำถามด้วย SQL template ตรงใน Cloudflare Worker + D1 — ไม่ใช้ชั้น homelab (②) ในเฟสนี้**

เหตุผล:
1. เกทของ P2 คือ **"20 คำถามมาตรฐาน"** = ชุดคำถามที่รู้ล่วงหน้า ไม่ใช่ NLU อิสระเปิดกว้าง ⇒ จับคู่
   keyword/pattern → SQL query ตรงตาราง `task`/`task_event`/`person` → ประกอบคำตอบเป็นข้อความไทย
   **รับประกันไม่มีวันแต่งคำตอบ** (ตรงเป้าหมายเกทเป๊ะ ดีกว่า LLM ที่ต้องกันหลอนเพิ่ม)
2. ชั้น homelab (เต้น้อย) ตามแผนเดิมยังไม่พร้อมใช้งานจริง — โปรเจกต์เครื่อง Ollama แยกยังรอจัดซื้อ (memory:
   `ollama-dedicated-machine-project`) ผูกกับชั้นนี้ตอนนี้ = รอจัดซื้อก่อนถึงเริ่ม P2 ได้ ไม่ตรงกับ "ไล่ไปเลย"
3. Worker ฟรี + D1 ฟรี ที่มีอยู่แล้วพอสำหรับ query แบบ template — ไม่เพิ่มต้นทุน ไม่เพิ่มจุดเสี่ยงใหม่
4. ถ้าอนาคตต้องการ NLU อิสระเต็มรูปแบบ (ถามอะไรก็ได้ ไม่ใช่แค่ 20 แบบ) — ค่อยเพิ่มชั้น homelab เป็นเฟส
   แยกทีหลัง ไม่ใช่เงื่อนไขเริ่ม P2

**ถ้าพี่เต้อยากได้ NLU อิสระตั้งแต่ P2 เลย (ไม่ใช่แค่ template) บอกได้ — จะออกแบบใหม่ให้พึ่ง homelab แทน**
ค่าเริ่มต้นเอกสารนี้ยึด SQL template ไว้ก่อน เพราะตรงเกทและเริ่มได้ทันที

## 1. แบ่งงาน — A ปลอดภัย (คลาวด์ล้วน) ก่อน B แตะ LIVE

### ชุด A — Read model + query engine (คลาวด์ล้วน ไม่แตะ vendor-ksk เลย)

#### WP-P2-A1 · สิทธิ์การมองเห็น (visibility model)
`person.role` และ `person.department` **มีอยู่แล้วทั้งคู่ตั้งแต่ P0** (ตรวจ schema จริงแล้ว — ไม่ต้องเพิ่ม
คอลัมน์ใหม่) ตอนนี้มีแค่แถวเดียว: `P-EKAPUN` / `department='management'` / `role='owner'` — กำหนดกฎ:
- `role = 'worker'` → เห็นเฉพาะ `task.assignee_person_code = ตัวเอง`
- `role = 'manager'` → เห็นทุกคนใน `department` เดียวกัน
- `role = 'owner'` → เห็นทุกคนทุกแผนก

**ฟังก์ชันใหม่ `worker/src/visibility.ts`:** `canView(actorPersonCode, targetPersonCode): Promise<boolean>`
ทุก query engine (A2) ต้องเรียกผ่านนี้ก่อนคืนผล — จุดเดียวที่ตัดสินสิทธิ์ (เหมือนที่ `taskMachine.ts`
รวม authorization check ไว้จุดเดียวใน P1-B1)

#### WP-P2-A2 · Query engine (20 คำถามมาตรฐาน)
`worker/src/queryEngine.ts` — จับคู่ pattern คำถามภาษาไทย → SQL query ผ่าน D1 → ประกอบคำตอบ

**ชุดคำถามเริ่มต้น (แบ่ง 3 กลุ่ม, ครบ 20 ข้อ):**

*กลุ่มงานของตัวเอง (ทุก role ถามได้):*
1. งานของฉันมีอะไรบ้าง
2. งานที่ค้างอยู่ตอนนี้
3. งานที่เกินกำหนดแล้ว
4. งานที่เสร็จวันนี้
5. งานที่เสร็จสัปดาห์นี้
6. งานถัดไปที่ต้องทำ
7. งานล่าสุดที่ได้รับมอบหมาย

*กลุ่มสถานะทีม (เฉพาะ manager/owner — ต้องผ่าน `canView` ก่อนตอบ):*
8. ใครยังไม่รับงาน (status=assigned ค้างนานกว่า X)
9. ใครมีงานค้างมากที่สุด
10. งานที่เกินกำหนดของทีม
11. สรุปงานวันนี้ทั้งทีม
12. ใครปฏิเสธงานบ้าง (status=rejected)
13. งานที่ยังไม่มีคนรับ (assignee ว่าง — ยังไม่มี field นี้ใน P1 ต้องเช็ค schema)

*กลุ่มประวัติ/สถิติ:*
14. งานเสร็จกี่ใบเดือนนี้
15. งานถูกปฏิเสธกี่ใบเดือนนี้
16. เวลาเฉลี่ยตั้งแต่รับงานถึงเสร็จงาน
17. ใครรับงานเร็วที่สุด (เฉพาะ manager/owner)
18. วันนี้มีงานใหม่กี่ใบ
19. คำถามนี้ AI Manager ทำอะไรได้บ้าง (help/เมนู)
20. สถานะระบบ (สุขภาพ ingest ล่าสุดเมื่อไหร่ — ผูกกับ `sync_state`/`ledger` ที่มีอยู่แล้ว)

**หลักการคำตอบ:** ทุกคำตอบต้องมาจาก query จริงเท่านั้น ไม่มี template คำตอบลอยๆ ที่ไม่ผ่าน DB
ถ้า pattern ไม่ตรงคำถามไหนเลย → ตอบ "ยังไม่เข้าใจคำถามนี้ ลองพิมพ์ 'AI ช่วยอะไรได้บ้าง'" (ไม่เดา ไม่แต่ง)

#### WP-P2-A3 · เทส
- ครบ 20 คำถามมาตรฐาน มีเทสอย่างน้อย 1 เคสต่อข้อ ยืนยันคำตอบตรงกับข้อมูลที่ seed ไว้จริง
- เทส cross-visibility: worker ถามคำถามกลุ่ม 2 (สถานะทีม) ต้องถูกปฏิเสธ/ไม่เห็นข้อมูลคนอื่น
- เทส unmatched question: คำถามที่ไม่ตรง pattern ไหนเลย ต้องตอบข้อความ "ไม่เข้าใจ" ไม่ใช่ error/crash

**ประตูของชุด A:** รันเทสในเครื่องผ่านครบ 100% ก่อนแตะ LIVE

### ชุด B — ช่องทางถาม-ตอบผ่าน LINE จริง (⚠ แตะ LIVE อีกครั้ง รอคำอนุมัติแยกเหมือนทุกรอบที่ผ่านมา)

#### WP-P2-B1 · ตัวดักคำถามฝั่ง vendor-ksk (ป้องกันชนกับ NLU เดิม)
vendor-ksk มี AI chat feature ("น้องกุ้ง") อยู่แล้วที่ดักคีย์เวิร์ดของตัวเอง (ลา/5ส/เครื่องมือ) — ต้องไม่ให้
คำถาม AI Manager ไปชนหรือถูกฟีเจอร์เดิมตอบขวางก่อน

**เสนอ:** ต้องพิมพ์ prefix ชัดเจน `"AI "` หรือ `"ai "` นำหน้าเสมอ (เช่น `"AI งานของฉันมีอะไรบ้าง"`) —
ตรวจจับ prefix นี้ **ก่อน** NLU เดิมของ vendor-ksk ทำงาน (แทรกจุดตรวจใหม่ใน `ll_handle_text()` ก่อนขั้นตอน
ที่มีอยู่) ถ้าตรง prefix → ไม่ให้ NLU เดิมประมวลผลต่อ ส่งเข้าคิว forward เข้าคลาวด์แทน (แบบ synchronous รอ
คำตอบจากคลาวด์ก่อน reply กลับ — คำถามต้องได้คำตอบทันที ไม่ใช่ fire-and-forget แบบ `aim_forward_events` เดิม)

**ข้อควรระวัง (เรียนจากบทเรียน `forceTask regex กันตัวจำแนกตีตก`ใน ARCHITECTURE.md เดิม):** ต้อง**ทดสอบว่า
prefix ตรวจจับได้แม่นยำ ไม่ชนกับข้อความปกติที่บังเอิญขึ้นต้นด้วย "ai"** ก่อน deploy จริง

#### WP-P2-B2 · endpoint รับคำถาม + ตอบกลับ (synchronous ต่างจาก B1 ของ P1 ที่เป็น async)
คำถาม-ตอบต้องเร็ว (ผู้ใช้รอคำตอบอยู่) — ต่างจาก task card ที่ fire-and-forget ได้ ต้องออกแบบเป็น
**request-response ตรง** ไม่ใช่คิว: vendor-ksk เรียก endpoint ใหม่บนคลาวด์ (เช่น `POST /ask`) แนบคำถาม+
person_hash → Worker query D1 ทันที → ตอบ JSON กลับใน response เดียวกัน → vendor-ksk reply เข้า LINE

**timeout:** ต้องตอบภายในไม่กี่วินาที (LINE reply token หมดอายุเร็ว) — คิวแบบ P1 ใช้ไม่ได้กับงานนี้

#### WP-P2-B3 · สรุปเช้า-เย็น (Cron)
ใช้ Cloudflare Cron ที่มีอยู่แล้ว (P0-4) เพิ่มงานใหม่: เวลาที่กำหนด (เช่น 08:00/17:00) → query สรุปของแต่ละ
`manager`/`owner` → เรียก endpoint ส่งข้อความสรุปเข้า LINE (คล้าย `aim_notify.php` แต่เป็นข้อความสรุปแทนการ์ด)

**ประตูของชุด B (= ประตูรวมของ P2):**
- 20 คำถามมาตรฐาน ถามผ่าน LINE จริง ได้คำตอบตรงข้อมูลจริงครบทุกข้อ ไม่มีคำตอบไหนแต่งขึ้น
- ลูกน้องถามงานคนอื่นผ่าน LINE จริง ต้องไม่เห็นข้อมูล (ทดสอบกับคนทดสอบคนที่สอง — ต้อง bootstrap เพิ่ม)
- สรุปเช้า-เย็น ส่งถึงจริงตามเวลาที่ตั้ง อย่างน้อย 3 วันติดไม่ขาด

## 2. ลำดับที่จะทำ
1. WP-P2-A1 (visibility model) — เริ่มได้ทันที ปลอดภัย
2. WP-P2-A2 (query engine 20 คำถาม) — ต่อจาก A1
3. WP-P2-A3 (เทสครบ) — ปิดชุด A
4. รอคำอนุมัติแยกก่อนเริ่มชุด B (เหมือนทุกรอบที่ผ่านมาที่แตะ LIVE)
5. WP-P2-B1 → B2 → B3 → ทดสอบเกทเต็ม

## 3. หลังจาก P2 ปิดเกท
ต่อ **P3 (ความคิดริเริ่ม)** — ต้องมีข้อมูลจริงจาก P2 ใช้งานสักพักก่อนออกแบบ escalation policy ให้ตรงพฤติกรรม
จริง (ไม่ใช่เดาจากสเปคอย่างเดียว) — จะเขียน `WORK_PACKAGES_P3.md` ตอนถึงจุดนั้น ไม่ออกแบบล่วงหน้าเกินไปตอนนี้
เพราะรายละเอียดจะเปลี่ยนตามสิ่งที่เจอจริงใน P2
