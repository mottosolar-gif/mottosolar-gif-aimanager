## 3. ที่เบี่ยงจากแผนแล้วดีกว่า — รับเป็นมาตรฐาน

1. **สมองอยู่ชั้น ③** — ข้อมูลจริงและสิทธิ์เขียนอยู่ที่นั่น ตอบจากที่เดียวกับที่เขียน = ไม่มีความจริงสองชุด
2. **คลาวด์ไม่มี LLM (ตั้งใจ)** — ตอบด้วย SQL + จับคำตายตัว ⇒ ไม่หลอน ไม่กินโควตา ตรงกับกติกา "ไม่มั่นใจ = ไม่เดา"
3. **ความไวที่หวังจากชั้น ① ได้จากเครื่องเราเอง** — webhook spool ตอบ 200 ใน ~100 ms
4. **ฟีดกลุ่มย้ายมาอยู่ฐานเรา** (`gf_serves`) ⇒ homelab หลุดจากเส้นทางวิกฤตของงานประจำวัน

## 4. ที่เบี่ยงแล้วเป็นหนี้ — ต้องแก้

1. `person_link` ยังต้องรัน `bin/aim_link_person.php --all` ด้วยมือ ⇒ **คนที่เพิ่งได้สิทธิ์จะโดนคลาวด์ตอบ 403
   "บัญชียังไม่เปิด" ทั้งที่หน้าเว็บบอกว่าสิทธิ์ครบ** (D-P0-14 ข้อ 1)
2. **4 คิวรีใน `worker/src/db/queries.ts` ไม่มีตัวกรองสถานะ** (บรรทัด 222 · 333 · 452 · 553/584)
   วันนี้รอดเพราะ `task_event` ว่างและ `accepted_at` ว่างทั้งฐาน — **รอดเพราะบังเอิญ ไม่ใช่เพราะมีด่าน**
3. **กระจกงานเป็นครึ่งใบ** — ทุกใบเป็น `L-` ⇒ `applyTransition()` ปฏิเสธตั้งแต่บรรทัดแรก (`taskMachine.ts:85-87`)
   ⇒ `task_event` ไม่มีวันมีแถว ⇒ intent สถิติที่อ่านจากตารางนั้นตอบจากข้อมูลที่ไม่มีทางมี
4. `outbound_queue` · `sync_state` สร้างไว้แต่ **ไม่มีโค้ดอ้างถึงเลย**
5. **ตัวนับสตรีค P4 แยกไม่ออกระหว่าง "ไม่ตรง" กับ "ยังไม่ได้วัด"** — วันที่ยามยังไม่รัน สตรีคกลายเป็น 0 ทันที
   (วันนี้: ข้อมูลตรงกัน 12 วันติด แต่ตัวนับรายงาน 0)
6. เอกสารล้าสมัย — `aim/CLAUDE.md` ยังเขียนว่า "ไม่มี remote · branch master · CI ไม่เคยรัน" (ผิดหมดแล้ว)
   และ WP-P0-5 ยังอ้างว่าขาด `bin/smoke_aim_forward.php` ทั้งที่ไฟล์มีอยู่จริง ⇒ **ใบนั้นปิดได้แล้ว**

## 5. แผนที่เคาะแล้ว (2026-09-10)

**ปลายทางยังเป็น Cloudflare** ตาม D-2026-08-29-ก — แต่ **เปลี่ยนทางเดิน**: ไม่ย้ายสมองทีละชิ้น
เพราะการย้ายตรรกะไม่ได้แก้เรื่องที่เจ็บจริง (cim-server เป็นจุดตายจุดเดียว) และ 3 ใน 5 ชิ้นที่เคยเสนอ
พิสูจน์แล้วว่าไม่คุ้ม (รายละเอียดข้อ 6)

**ขั้นที่ 1 — ปิดหนี้ที่รู้อยู่แล้ว (ไม่ย้ายอะไรเลย)**
- `person_link` ต้องเกิดเองจากทะเบียนจริง ไม่ต้องรอคนรันสคริปต์
- ใส่ตัวกรองสถานะให้ 4 คิวรีที่ขาด
- ตัวนับสตรีคต้องแยก "ไม่ตรง" ออกจาก "ยังไม่ได้วัด"
- แก้เอกสารที่ล้าสมัย + push งานค้าง 11 คอมมิตให้ CI เห็น

**ขั้นที่ 2 — ด่านหน้า LINE บน Cloudflare แบบ store-and-forward**
รับ webhook แล้วส่งต่อเข้าบ้าน (รูปแบบเดียวกับ `mottosolar-line-relay` ที่รันจริงอยู่แล้ว)
- เครื่องในบ้านดับ = ข้อความพักในคิว **ไม่หาย** ⇒ ได้ "ความทน" ซึ่งเป็นสิ่งเดียวที่คลาวด์ให้ได้จริง
- **ไม่ย้ายความจริงสักตาราง ไม่แตะสิทธิ์ ไม่แตะตรรกะ**
- ถอยกลับ = เปลี่ยน URL ใน LINE console

**ขั้นที่ 3 — ค่อย mirror ตารางอ่านทีละตัวตาม D-P0-18** (คงกติกา "LIVE เป็นเจ้าของ คลาวด์อ่าน")

## 7. เงื่อนไขหยุด (ถ้าเจอข้อใดข้อหนึ่ง = หยุดย้าย)

- ขั้นไหนต้องเขียนกลับฐาน LIVE หรือมีสองที่เขียนตารางเดียวกันแม้ชั่วคราว
- ไม่มี `--rollback` ที่ซ้อมบน clone แล้ว (มาตรฐานเดียวกับ `move_line_user.php`)
- reconcile ไม่ตรงกัน 2 วันติดหลังสลับ
- p95 ของคำตอบแย่กว่าเดิม (chat 3.7 วิ · fim_qa 20 วิ) หรือ LINE เริ่มนับ webhook ว่าล้ม (>10 วิ)
- invocation ทั้งบัญชีเกิน 60%/วัน
- ต้องซ่อมสองภาษา (PHP + TS) ในเหตุการณ์เดียวเกิน 1 ครั้ง/เดือน — ทีมมีคนดูแลจริงคนเดียว

## 7ข. เจอระหว่างทางแต่ **ไม่อยู่ในแผน** (เจ้าของระบบสั่ง 2026-09-10: "ยึดตามแผน — เรื่องพวกนั้นมีมาก่อน as-built")

- `php.ini` ไม่ตั้ง `date.timezone` ⇒ entry point ที่ไม่ตั้งเองทำงานใน UTC · สำรวจแล้ว: ไม่มี Task Scheduler
