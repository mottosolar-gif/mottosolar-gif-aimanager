## 2. สามด่านที่ต้องผ่านก่อนวาง DB ที่ homelab

### ด่าน 1 — สัญญาปัจจุบันห้ามไว้ (ต้องแก้สัญญา ไม่ใช่แค่เขียนโค้ด)
`CONTRACT_homelab.md §6` ประกาศเป็นกติกาถาวร: **"ตัวตนพนักงาน · สิทธิ์ · การแจ้งเตือนรายคน = ของ KSK
· ห้าม homelab สร้างซ้ำ"** — เหตุผลตอนนั้น: กันพนักงานเจอสองบอทถามเรื่องเดียวกัน + ข้อมูลสองฐานที่ไม่ตรงกัน
· การย้าย roster DB ไป homelab = **แก้สัญญาข้อนี้อย่างเป็นทางการ** (พี่เต้เป็นเจ้าของสัญญา แก้ได้
แต่ต้องจดเป็นลายลักษณ์ + ให้ฝั่ง homelab รับรู้) — และต้องนิยามใหม่ให้คม: homelab เป็น "ที่เก็บ"
แต่**ตรรกะสิทธิ์ยังตัดสินฝั่งผู้ใช้ข้อมูล** เพื่อไม่ให้เกิดสองบอทจริง ๆ

### ด่าน 2 — homelab ยังไม่ผ่านเกณฑ์เป็น "บ้านของข้อมูลระบบคน" (วัดจริง)
| เกณฑ์ | สถานะวันนี้ |
|---|---|
| Availability | **72 ชม.ล่าสุด = 288/288 (100%)** · ย้อน 7 วันมีช่วงเงียบจริงครั้งเดียว: 25 ส.ค. 5.4 ชม. ⚠ **แก้ตัวเลขเดิม 2026-08-29:** เคยเขียนว่า "เงียบ 10 ชม. เมื่อ 22 ส.ค." — ผิด เพราะ heartbeat เพิ่งเริ่มส่ง 22 ส.ค. 10:42 ช่วงก่อนหน้านั้นคือ "ยังไม่เริ่มเก็บ" ไม่ใช่ "ล่ม" |
| **Backup** | 🔴 **D-009 จดไว้เอง: ข้อมูลบน homelab มีสำเนาเดียวคือเครื่องนั้น — เครื่องพัง = หายถาวร** · ยังไม่มีหลักฐานแผน backup ใด ๆ (ขณะ cim-server มี VM backup รายวัน retention 7) |
| ท่อเขียนข้ามเครื่อง | สะพาน v1 มีแค่ ping/note/ask/heartbeat — **ไม่มี CRUD** · การสั่งงานกลับ latency ~15 นาที ⇒ ต้องสร้าง API ใหม่ (มี precedent: MCP over tailnet — แต่ตัวนั้น read-only) |
| ประวัติของหาย | MCP tool เคยหายเงียบใน 10 นาที (team_followups) · เอกสารสัญญาเคยตามของจริงไม่ทัน |
| Classifier | AI ฝั่งโน้นถูกบล็อกตอนประกอบคำสั่งที่มีความลับ — ทุกอย่างต้องเป็น "สคริปต์เสิร์ฟสำเร็จ + อ่านกุญแจจาก .env" (บทเรียน D-008 heartbeat ที่ไม่เคยเริ่ม) |

**เงื่อนไขบังคับก่อนวางจริง: homelab ต้องพิสูจน์ backup อัตโนมัติที่กู้ได้จริง** — ทะเบียนพนักงาน
หายถาวร = ทุกระบบไม่รู้ว่าใครใช้ได้ ร้ายแรงกว่ารูปหาย

### ด่าน 3 — เทคนิคที่ใช้ท่าเดิมไม่ได้
- `staff_current()` พึ่ง **cross-DB JOIN ในเครื่องเดียว** (≥5 จุด) — ข้ามเครื่องทำไม่ได้ ต้องเปลี่ยนเป็น
  cache + event
- privacy ชั้นคลาวด์ (D-P0-01): ชื่อจริง/ข้อมูลบุคคล**ห้ามขึ้น Cloudflare** ⇒ roster ขึ้น D1 ตรง ๆ ไม่ได้
  — นี่แหละเหตุผลเชิงโครงสร้างที่ทำให้ "เก็บในบ้าน (homelab) + ให้คลาวด์เห็นแค่ pseudonym" เป็นคำตอบ
  ที่สอดคล้องกับกติกาที่มีที่สุด (D-P0-01 เขียนไว้แต่แรกว่า homelab = ชั้นข้อมูลภายใน)

## 3. สถาปัตยกรรมที่แนะนำ — "ทะเบียนกลาง 1 เจ้าของ + สำเนารู้อายุทุกผู้ใช้"

```
                       ┌─ LINE (การ์ดยืนยัน: เข้าใหม่/ลาออก/เปลี่ยนสิทธิ์)
   พี่เต้/แอดมิน ──────┤
                       └─ เว็บหน้าบริหาร (ช่วงแรกเสิร์ฟจาก vendor-ksk · ระยะยาวเป็น Worker ตาม D-P0-19)
                              │ เขียนผ่าน API เดียว (tailnet + กุญแจ + idempotent ref)
                              ▼
                ┌──────────────────────────────┐
                │  homelab: Employee Registry  │  ← เจ้าของความจริงหนึ่งเดียว
                │  (คน · สถานะจ้างงาน · สิทธิ์) │     เงื่อนไข: backup พิสูจน์ได้ก่อน
                └──────────────┬───────────────┘
              event push ทันที │ + full sync ตามรอบ (ตาข่ายรอง) + reconciler รายคืน
        ┌─────────────────────┼──────────────────────┐
        ▼                     ▼                      ▼
  vendor-ksk (cache      db_fim (รับ event        Cloudflare D1 (สำเนา pseudonym:
  ใน db_customs —        "ปิดบัญชี" → ปิด          person_code + active + สิทธิ์
  LINE bot อ่านที่เดิม    credential เว็บ)          — ไม่มีชื่อ = ไม่ขัด D-P0-01)
  ไม่ต้องรื้อ webhook)
```

**หลักที่ยกมาจากคำตัดสินเดิมทั้งหมด (ไม่ต้องคิดใหม่สักข้อ):**
- บอทเสนอ · คนยืนยัน · ระบบจำ (กติกา 2026-08-17) — การ์ด "พนักงานใหม่/คนนี้ลาออก?" ให้แอดมินกด
  ไม่ใช่ AI ตัดสินเอง
- ผูกบัญชี LINE ยังต้องแอดมินยืนยัน (P1) — registry ไม่เปลี่ยนเรื่องนี้
- Mirror → Dual-run → สลับเจ้าของ → ตัดของเก่า (D-P0-19) — roster ก็เดินลำดับนี้
- ส่งทั้งชุดทุกรอบ ไม่ทำ incremental (บทเรียน aim_task_sync) · `ref` UNIQUE กันซ้ำ (bridge)
- ห้าม ENUM (sql_mode ว่าง) · ผู้รับแจ้งเตือนไดนามิก `Is_Manager`

**Fail-safe ตอน homelab เงียบ (ตอบโจทย์ 96% availability):**
ทุกผู้ใช้ถือ **cache ล่าสุด + timestamp** — registry เงียบ = ใช้ cache ต่อ **ห้ามเตะใครออก ห้ามรับใครเพิ่ม**
จนกว่ากลับมา · เหตุผลที่ roster ทน cache เก่าได้ดีกว่างานอื่น: การจ้างงานเปลี่ยนช้า (ไม่มีใครลาออกทุก 15 นาที)
ข้อมูลเก่า 5 ชม. ของทะเบียนพนักงานยอมรับได้ · watchdog แจ้ง "ข้อมูลทะเบียนอายุเกิน X ชม." มีโครงอยู่แล้ว
(bridge_watchdog) ไม่ต้องสร้างยามใหม่

**สิ่งที่ห้ามย้ายไปด้วยในเฟสแรก:** รหัสผ่านเว็บ (credential) — แยก "การจ้างงาน" (registry ใหม่เป็นเจ้าของ)
ออกจาก "รหัสเข้าเว็บ" (db_fim เป็นเจ้าของต่อ ตาม H6 — บทเรียนรหัส 2 ชุดเจ็บจริงมาแล้ว) ·
มุมมอง: FIM ถูก**ลดบทบาท**จาก "เจ้าของตัวตนพนักงาน" เหลือ "เจ้าของ credential เว็บของตัวเอง" —
ซึ่งตอบคำถามเดิมของพี่เต้พอดี ("ยังต้องผูกไอดีอะไรใน FIM อีกไหม" → เหลือแค่นี้ และหดต่อเรื่อย ๆ)

## 4. โบนัสเชิงโครงสร้าง — ชิ้นนี้แก้หนี้เก่า 3 ใบพร้อมกัน

1. **หนี้ D-P0-14 ข้อ 1**: ไม่มีโค้ด production เขียน `person_link` — พนักงานคนที่ 3 ติด 403 ตลอดกาล
   ⇒ registry คือตัว provision `person`/`person_link` ให้คลาวด์โดยธรรมชาติ (onboarding ที่ขาดอยู่)
2. **งานค้าง MIGRATION_USER_SOURCE**: sync รายชั่วโมงที่ไม่เคยตั้ง — ถูกแทนด้วย event+sync ของ registry
3. **ช่องโหว่ LINE bot มองไม่เห็นการปิดบัญชี** (ข้อ 1) — ปิดถาวรด้วย cache ที่มีเจ้าของป้อน

และมันคือ **jigsaw ชิ้นที่ 2 ที่ควรมาก่อนการย้ายเครื่องมือ/5ส/ลา** — เพราะทุกระบบที่จะย้ายขึ้น Cloudflare
ต้องตอบ "ใครใช้ได้" ก่อนเสมอ · identity คือฐานของทุกชิ้นที่เหลือ · ทำช่วงรอสตรีค aim ได้พอดี
(คนละระบบ ไม่แตะตัวเทียบ P4)
