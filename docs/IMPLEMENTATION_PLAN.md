### ⚠ ข้อจำกัดที่ต้องรู้ก่อนออกแบบ (VERIFIED)

1. **โควตา LINE push — ไม่ใช่ข้อจำกัดจริง (แก้ 2026-08-27)**
   ถามจาก LINE API ตรง ๆ: `GET /v2/bot/message/quota` → `{"type":"limited","value":15000}` · `quota/consumption` → `{"totalUsage":610}`
   ⇒ **15,000 ข้อความ/เดือน ใช้ไป 610 เหลือ 14,390** (พี่เต้ทักเอง 27 ส.ค. ว่าตัวเลขที่ผมอ้างผิด — ตรวจแล้วพี่เต้ถูก)
   ⚠ `TEAM_TOOLS_INVENTORY.md` §A9 ยังเขียนว่า *"300/เดือน ใช้ไป ~200 งบตึง"* — **ตัวเลขนั้นผิด/ล้าสมัย และเอกสารนั้นถูกเสิร์ฟให้ฝั่ง homelab อ่านด้วย** ⇒ ต้องแก้ ไม่งั้นทั้งสองฝั่งจะออกแบบรัดเกินจริง
   ⇒ ประเมินภาระจริง: 11 คน × 30 วัน × 10 ข้อความ ≈ 3,300/เดือน = ~22% ของโควตา ⇒ push รายคนได้สบาย
   ⇒ ยังคงหลัก "reply ก่อน push" ไว้ (reply ไม่นับโควตาเลย) และส่งกลุ่ม = 1 ข้อความไม่คูณคน — แต่เป็นเรื่องความสุภาพต่อผู้ใช้ ไม่ใช่เพราะโควตาบีบ
2. **เครื่องนี้ deploy Cloudflare เองไม่ได้** — ไม่มี `wrangler` ไม่มี API token · MCP ที่ต่อ Cloudflare มีแต่เครื่องมืออ่าน
   ⇒ ต้องได้ token สิทธิ์ `Workers Scripts:Edit` หรือให้ homelab เป็นคน deploy
3. **ของฟรีเปลี่ยนเงื่อนไขได้เสมอ** — เอกสารบ้านนี้เขียนเตือนตัวเองไว้แล้ว ⇒ ทุกชิ้นต้อง **ย้ายบ้านได้** (ดู §5)

### ทำไมแบ่งแบบนี้

| ชั้น | เหตุผลที่ต้องอยู่ตรงนั้น |

## 3. ท่ออ่านจากเครื่องนี้ — เลือกแบบ "ยื่นออก" ไม่ใช่ "ให้เข้ามาดึง"

**ข้อเสนอ: cim-server เป็นฝ่ายส่งออกอย่างเดียว (outbound push)** ไม่เปิดทางให้ cloud เข้ามา

| ทางเลือก | ข้อดี | ข้อเสีย | ตัดสิน |
|---|---|---|---|
| A. เปิด API ให้ cloud เรียกเข้ามา | ข้อมูลสดที่สุด | ต้องเปิดผิวสัมผัสสาธารณะเพิ่ม + ต้องดูแลสิทธิ์/rate limit | ❌ |
| B. **cim-server ยิงสรุปออกไปเป็นจังหวะ** | ไม่เปิดพอร์ตใหม่เลย · แพทเทิร์นเดียวกับ heartbeat ที่ใช้ได้ผลมาแล้ว 646 รอบ | ข้อมูลช้าตามจังหวะที่ตั้ง | ✅ **เลือกข้อนี้** |
| C. ผ่าน tailnet ให้ homelab ดึง | ไม่ออกอินเทอร์เน็ต ปลอดภัยสุด | Cloudflare เข้าไม่ถึง ต้องผ่าน homelab เสมอ | ✅ ใช้คู่กับ B สำหรับข้อมูลอ่อนไหว |

**สิ่งที่ยิงออก:** สถานะงาน/ลา/เครื่องมือแบบสรุป — **ไม่ใช่ทั้งฐาน**
**สิ่งที่ห้ามออกจากเครื่องนี้เด็ดขาด:** ข้อมูลศุลกากรทุกชนิด · รหัสผ่าน · เลขใบขน · ราคา/มูลค่า

## 4. เรื่องข้อมูลออกนอกบริษัท — ต้องตัดสินก่อนเริ่ม (สำคัญที่สุดในแผนนี้)

พี่เต้พูดเองว่าบริการเหล่านี้ *"กำลังจ้องเทรน AI ตัวเอง เลยปล่อยฟรีเยอะ"* — ถูกต้อง และนั่นแปลว่า **ต้องเลือกว่าอะไรออกไปได้**

**ข้อเสนอ: ใช้รหัสแทนคน (pseudonym) บนบ้านนอก**

| ข้อมูล | บนคลาวด์เก็บอะไร | ชื่อจริงอยู่ที่ไหน |
|---|---|---|
| คน | `W07` · แผนก · บทบาท | cim-server เท่านั้น |
| งาน | หัวข้องาน · สถานะ · เวลา | เหมือนกันทั้งสองที่ |
| ใบลา | ประเภท · ช่วงวัน | **เหตุผลการลาไม่ออกจากบ้าน** |
| รูป | ลิงก์ + ผลวิเคราะห์ | ไฟล์จริงอยู่ homelab (D-009 ตัดสินไว้แล้ว) |

⇒ ต่อให้ผู้ให้บริการเอาข้อมูลไปเทรน ก็ได้แค่ "W07 ปิดงานช้า 2 ใบ" ไม่ใช่ชื่อพนักงานจริง
⇒ ต้นทุน: ต้องมีตารางแมป และทุกข้อความที่ส่งถึงคนต้องแปลงกลับเป็นชื่อจริง **ที่ชั้น ② หรือ ③ เท่านั้น**

## 5. กฎกันติดกับดักของฟรี (ต้องมีตั้งแต่บรรทัดแรก)

1. **ฐานข้อมูลต้องย้ายบ้านได้** — ใช้ SQL มาตรฐาน · ห้ามใช้ฟีเจอร์เฉพาะเจ้าใดจนย้ายไม่ได้
2. **ส่งออกได้ทุกวัน** — dump ข้อมูลกลับมาเก็บที่ cim-server อัตโนมัติ (ของฟรีปิดบริการได้ทุกเมื่อ)
3. **ตรรกะธุรกิจห้ามอยู่ใน Notion/บริการสำเร็จรูป** — Notion เป็น "จอ" เท่านั้น ความจริงอยู่ในฐานของเรา
4. **ทุกบริการต้องมีแผนสำรอง 1 บรรทัด** เขียนไว้ล่วงหน้าว่าถ้าเจ้านี้ปิด ย้ายไปไหน
5. **ห้ามผูกบัตรเครดิตกับบริการที่คิดเงินตามการใช้** โดยไม่มีเพดาน (Firebase Functions ต้องระวังข้อนี้)

## 6. ลำดับงาน (เฟส) + ประตูที่ห้ามข้าม

### P0 · ท่อและกระดูก (ยังไม่มีฟีเจอร์)
- repo ใหม่บน GitHub · Actions deploy ขึ้น Cloudflare อัตโนมัติ
- Worker รับ webhook + คิว + ฐาน + Cron ว่าง ๆ ที่ยังไม่ทำอะไร
- ท่อ read-only จาก cim-server (แบบ B) ยิงข้อมูลสรุปออกทุก N นาที
- **ประตู:** ข้อความจากกลุ่มทดสอบเดินทางครบวง (LINE → Worker → คิว → homelab → เขียนฐาน → ตอบกลับกลุ่ม) และมี log ทุกจุด

### P1 · ประสาทสัมผัส (สเปค §7–§11)
งาน + สถานะครบ 12 + รับ/ปฏิเสธ/กำลังไป/ถึงแล้ว/รูป/ปิดงาน + idempotency
- **ประตู:** เดินครบเส้นทางในกลุ่มทดสอบ · ยิงซ้ำ 3 ครั้งไม่เกิดงานซ้ำ

### P2 · สายตา + ปาก (ตอบข้อ ① ของพี่เต้)
read model + ตอบคำถามจากข้อมูลจริง + สรุปเช้า-เย็น + **สิทธิ์การมองเห็นรายคน**
- **ประตู:** 20 คำถามมาตรฐาน ไม่มีคำตอบไหนแต่งขึ้น · ลูกน้องถามงานคนอื่นต้องไม่เห็น

### P3 · ความคิดริเริ่ม (สเปค §15–§17)
watcher + escalation 4 ระดับ + ชั้นกฎ AUTO/PROPOSE/ASK + สมุดบันทึกการตัดสิน
- **ประตู:** จำลอง 10 สถานการณ์ได้ผลตามกฎทุกครั้ง · ไม่เตือนซ้ำเกิน 1 ครั้งต่อระดับ · **นับโควตา push ที่ใช้จริงต่อวัน**

### P4 · ทดสอบเต็มระบบ (คำสั่งข้อ ⑤)
รันคู่ของเดิม ≥ 2 สัปดาห์ในกลุ่มทดสอบ + คนจริงกลุ่มเล็ก · เทียบผลทุกคืน
- **ประตู:** ผลตรงกัน 100% ติดกัน 7 วัน · โควตา push ต่อเดือนไม่เกินที่มี

### P5 · ทยอยย้ายระบบขึ้น Cloudflare ทีละชิ้น (แก้ 2026-08-29 ตาม D-2026-08-29-ก)
> ฉบับเดิมเขียนว่า "ย้ายของจริง แล้วค่อยตัดสาย CIM · แก้ 12 ไฟล์ CIM" — **ตัดสาย CIM จบไปแล้ว**
> (นับใหม่ได้ 0 ไฟล์ ไม่ใช่ 12 — เว็บ CIM ตายตั้งแต่ 23 ก.ค. ก่อนแผนนี้ถูกเขียน)
> เจ้าของระบบเปิดเผยเป้าหมายจริงที่ตัดสินไว้แล้ว: **aim คือ jigsaw ชิ้นแรกที่พิสูจน์ pattern
> "ระบบบน Cloudflare" — ถ้าได้ผล จะทยอยย้าย เครื่องมือ → 5ส → ลา → งาน → LINE bot ตามไปทีละชิ้น**
> เพื่อออกจากสภาพเครื่องเดียวรันทุกอย่าง

แต่ละระบบเดินลำดับขั้นเดียวกับที่ aim เดินผ่านมาแล้ว (รายละเอียดเต็มใน D-2026-08-29-ก):
**1. Mirror ทางเดียว → 2. Dual-run เทียบผล 7 วันติด → 3. สลับความเป็นเจ้าของ (คำตัดสินรายระบบ
+ แผนถอยกลับ) → 4. เฝ้าดู แล้วค่อยตัดของเก่า**
- **ประตูของขั้น 2 ทุกระบบ = ประตูเดียวกับ P4:** ตรงกัน 100% ติดกัน 7 วัน (reconciler + streak)
- **ประตูของขั้น 4:** ยามยืนยันว่าของเก่า "หยุดจริง" ไม่ใช่แค่ของใหม่ทำงาน
- D-P0-18 (ความจริงอยู่ LIVE) ยังบังคับใช้กับทุกระบบจนกว่าระบบนั้นถึงขั้น 3 ของตัวเอง

## 10. สิ่งที่แผนนี้ไม่ทำ

- ไม่แตะข้อมูล/โค้ดศุลกากร

- ไม่ให้ AI ตัดสินเรื่องคน/เงิน/สิทธิ์เอง
- ไม่ผูกบัตรเครดิตกับบริการที่คิดเงินตามการใช้โดยไม่มีเพดาน
