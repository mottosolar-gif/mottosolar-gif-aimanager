# โครงร่าง "บอทเดียว หลายบริษัท" — แขวนไว้ (ร่าง 2026-09-11)

> **สถานะ: แขวน** — เจ้าของระบบเปิดเผย 2026-09-11 ~08:20 ว่า *"นี่คือเหตุผลจริง ๆ ที่ทำเรื่องนี้: ใช้บอทเดียวหลายบริษัท"*
> และเคาะเองว่า **เป็นโปรเจกต์เขียนใหม่ ตั้งใบใหม่ ไม่ต่อจากใบ AI Manager** (LINE token + ฐาน + นโยบาย PII ใหม่ทั้งชุด)
> ไฟล์นี้มีไว้ให้ "เห็นโครงสร้าง" ก่อนตัดสินใจเริ่ม — **ไม่ใช่ใบสั่งงาน** · ห้ามเริ่มเขียนโค้ดจากไฟล์นี้จนกว่าจะมีคำสั่งเปิดใบ
> เขียนจากสิ่งที่พิสูจน์แล้วในโปรเจกต์ AI Manager (2026-08-27 → 09-11) — อะไรใช้ต่อได้ อะไรต้องทิ้ง อะไรที่คราวนี้ต้องมีตั้งแต่วันแรก

## 0. ความต่างจาก AI Manager ในประโยคเดียว

AI Manager = **บอทของบริษัทเดียว ที่สมองและความจริงอยู่ในบ้าน คลาวด์เป็นกระจก**
บอทหลายบริษัท = **สมองอยู่คลาวด์ ความจริงของแต่ละบริษัทอยู่คนละที่ (บางรายไม่มีเลย) คลาวด์ต้องพูดกับ LINE เองได้**
⇒ สามข้อที่ AI Manager ตัดสินว่า "ไม่ทำ" (ย้ายสมอง · LINE token บนคลาวด์ · PII ออกจากบ้าน) กลายเป็น**ข้อบังคับ**ของโปรเจกต์นี้ — จึงต้องเป็นใบใหม่ ไม่ใช่ต่อใบเดิม

## 1. ผัง

```
 บริษัท A (OA-A)      บริษัท B (OA-B)      บริษัท C (OA-C)        ← LINE OA คนละตัว token คนละดวง โควตา push แยก
      │ webhook            │ webhook             │ webhook
      ▼                    ▼                     ▼
 ┌──────────────────────────────────────────────────────────────┐
 │  Worker "gateway"  (ตัวเดียว)  — ตรวจลายเซ็นด้วย secret ของ OA นั้น │
 │  · ระบุ tenant จาก destination/channel id  · ตอบ 200 ทันที      │
 │  · เข้าคิว (Queues) → ตัวประมวลผลทำต่อ (LLM 4–8 วิ ไม่บล็อก)     │
 └──────────────┬───────────────────────────────────────────────┘
                ▼
 ┌──────────────────────────────────────────────────────────────┐
 │  Worker "brain"  — สายตอบเรียงตายตัว (บทเรียน 11 ก.ย.)           │
 │   1) intent engine ต่อ tenant  (กฎ + คำพ้อง · 150 ms · ไม่มี LLM) │
 │   2) สารบัญความรู้ต่อ tenant   (ตรวจ *หลัง* intent เท่านั้น)       │
 │   3) LLM ท้ายสุด  = tool-calling เข้า data adapter ไม่ใช่เดาอิสระ  │
 │   + ตัวนับ ask_miss / ตัดกลาง / ช้า  ต่อ tenant ตั้งแต่วันแรก        │
 │  สิทธิ์: canView(tenant, role)  ·  ทะเบียนคน: person(tenant)       │
 └──────┬───────────────────┬───────────────────┬────────────────┘
        ▼                   ▼                   ▼
   Data adapter A      Data adapter B      Data adapter C
   "hosted"            "sidecar"           "hosted"
   ตาราง D1 ของ A       ← ตัวดึง/ตัวส่งในบ้าน B   ตาราง D1 ของ C
   (บอทเป็นความจริง)     (ความจริงอยู่บ้าน B —      (บริษัทไม่มีระบบเดิม)
                         แบบ KSK วันนี้: sync
                         ทางเดียว + notify กลับ)
        │                   │                   │
        └────────── ตอบกลับ LINE จาก Worker โดยตรง (token ของ tenant นั้น) ──────┘
```

**KSK = tenant แรก แบบ "sidecar"** — ท่อ `/sync/tasks` ทางเดียว + `aim_notify` กลับบ้าน ที่พิสูจน์แล้ว 12 วันติด คือ adapter ตัวแรกที่มีอยู่แล้ว ไม่ต้องเขียนใหม่ · ต่างจากวันนี้แค่: Worker ถือ token ของ OA KSK และรับ webhook เอง

## 2. ห้าเรื่องที่ต้องตัดสินก่อนเปิดใบ (แต่ละข้อเปลี่ยนโครงสร้างจริง)

| # | เรื่อง | ทางเลือก | ที่แนะนำ + เหตุผล |
|---|---|---|---|
| 1 | **LINE OA** ตัวเดียวทุกบริษัท หรือ OA คนละตัว | ตัวเดียว = ถูก ง่าย แต่โควตา push รวมกัน · ชื่อบอทเดียว · กลุ่ม LINE รับ OA ได้ตัวเดียว (ข้อจำกัดจริงที่เจอ 2026-09-04) · คนเดียวอยู่ 2 บริษัทแยกไม่ออก | **OA คนละตัว** — token/secret/โควตาแยก · แบรนด์ของแต่ละบริษัท · ค่า LINE plan บริษัทจ่ายเอง · gateway ตัวเดียวรับได้หลาย OA (route ด้วย `destination`) |
| 2 | **ความจริงอยู่ไหน** | hosted (D1 ของ tenant · บอทเป็นระบบ) / sidecar (บ้านของ tenant เป็นเจ้าของ · คลาวด์กระจก) | **รองรับทั้งสองแบบผ่าน interface เดียว** `TaskSource · PersonRegistry · KnowledgeSource · Notifier` — KSK ใช้ sidecar (D-P0-18 ยังจริง) · บริษัทที่ไม่มีระบบใช้ hosted · ห้ามมี tenant ที่เขียนสองที่ (เงื่อนไขหยุดเดิม) |
| 3 | **PII** | นโยบายเดิม D-P0-01 "ข้อมูลคนไม่ออกจากบ้าน" ใช้ไม่ได้กับ hosted tenant | เขียนใหม่ต่อ tenant: เก็บ**น้อยที่สุดที่ตอบได้** (รหัสแทนตัว + ชื่อเล่น + บทบาท) · ข้อความดิบไม่เก็บ (คงไว้) · พรอมต์ LLM ใช้รหัสแทนชื่อ · retention ต่อ tenant · ใบยินยอมต่อ tenant · region ของ D1 ระบุ · "ลบบริษัทออก = ลบครบใน 1 คำสั่ง" ต้องมีตั้งแต่วันแรก |
| 4 | **LLM ใครจ่าย · โมเดลไหน** | บอทจ่ายรวม / tenant ถือคีย์เอง | tenant ถือคีย์เอง (secret ต่อ tenant) · บอทนับ token ต่อ tenant ลง `ai_usage(tenant)` · ตัดกลาง/ว่าง/ช้า จดตั้งแต่วันแรก (บทเรียน 11 ก.ย.: Ok ต้องไม่ใช่ HTTP 200) |
| 5 | **ภาษา** | ไทยอย่างเดียว / ไทย+อังกฤษ | กฎ intent สองภาษาตั้งแต่ต้น (วันนี้เพิ่งเติมอังกฤษ 4 intent) · คำตอบ mirror ภาษาที่ถาม · เมนู/การ์ดมีสองภาษา |

## 3. ของจาก AI Manager ที่ใช้ต่อได้ทันที vs ต้องทิ้ง

| ใช้ต่อได้ (พิสูจน์แล้ว) | ต้องเขียนใหม่ |
|---|---|
| โครง Worker + D1 (`ingest/sync/ask/link/admin/healthz`) · schema `person · person_link · task · ledger` — เติมคอลัมน์ `tenant_id` ทุกตาราง | **สมอง PHP 6 ชั้น** (`aim_ask` · kb · fim_qa · qa_index · group_fact · banter) → TS ต่อ tenant · ตรรกะไทยที่จ่ายบั๊กมาแล้วต้องมี corpus ยามก่อนย้ายทุกชิ้น |
| intent engine 20 intent + คำพ้อง + 414 เทส · แนวคิด "intent ก่อน สารบัญหลัง LLM ท้ายสุด" | **LINE reply/push จาก Worker** (วันนี้ไม่มี) · ตรวจลายเซ็นต่อ OA · rich menu ต่อ tenant |
| replay harness + corpus 62 ข้อ (`llm_replay --gate`) — ทำเป็น corpus ต่อ tenant | **webhook spool ฝั่ง PHP** → Cloudflare Queues (paid) หรือ `waitUntil` + push แทน reply |
| ตัวนับ ask_miss · ตัวห่อ LLM ที่จดตัดกลาง · selfcheck/streak/reconcile pattern | **นโยบาย PII + DATA_POLICY** ทั้งฉบับ (ข้อ 3) |
| GitHub-first · Workers Builds · ยามต้องแดงได้ · ผู้เขียน ≠ ผู้ตรวจ · ทีมเอเจนต์ | ทะเบียนคน: จากไฟล์/ฐานบ้าน → `person(tenant)` บนคลาวด์ + หน้าจัดการต่อ tenant |
| sidecar KSK (`aim_task_sync` · `aim_notify` · reconcile 7 วัน) = adapter ตัวแรก | ทุกฟีเจอร์ที่ "เขียนฐานบ้าน" (ลา · ลงเวลา · เครื่องมือ · 5ส · แนบรูป) — ต่อ tenant ต้องเลือก hosted/sidecar ทีละฟีเจอร์ |

## 4. ลำดับที่ปลอดภัย (ถ้าเปิดใบ) — ทุกขั้นถอยได้ด้วยเปลี่ยน URL/สวิตช์เดียว

## 5. ต้นทุน/ข้อจำกัดที่ต้องรู้ก่อน (ของฟรีมีเพดาน — กติกา §5 เดิม)

- Workers ฟรี 100,000 invocation/วัน **ต่อบัญชี** (relay ของ homelab ใช้ ~22% แล้ว · cron aim 1,440/วัน) ⇒ หลาย tenant + Queues = **Workers Paid** (~$5/เดือน) แทบแน่นอน · Queues/Durable Objects อยู่ใน paid
- LINE: OA ต่อบริษัท · โควตา push ตาม plan ของบริษัทนั้น (KSK วันนี้ 15,000/เดือน ใช้ 13%) · **กลุ่มหนึ่งรับ OA ได้ตัวเดียว**
- LLM: 4–8 วิ/คำตอบ ไม่ว่าอยู่ที่ไหน ⇒ ต้อง async (คิว + push) ไม่ใช่ reply ในคำขอเดียว · ค่า token ต่อ tenant
- D1: SQLite ต่อฐาน · ควร **1 ฐานต่อ tenant** (ลบ/ย้าย/สำรองทีละบริษัทได้) ไม่ใช่ตารางรวมใส่ `tenant_id` อย่างเดียว — แลกกับ query ข้ามบริษัทที่ไม่ควรมีอยู่แล้ว
- ไม่มี wrangler/token บนเครื่องบ้าน (ตั้งใจ) ⇒ ทุกอย่างผ่าน Workers Builds ต่อไป

## 6. สิ่งที่ห้ามทำซ้ำ (จ่ายบทเรียนมาแล้วในโปรเจกต์นี้)

- สารบัญความรู้ยืนหน้าเครื่องตอบข้อมูล (11 ก.ย.: 8/40 ถูกชิงตอบ)
- กฎ intent เขียนจากประโยคที่ผู้เขียนคิดเอง — ต้องมี corpus ภาษาแชทก่อน (10/40 → 39/41)
- ตัวห่อ LLM จด Ok จาก HTTP 200 (ตัดกลางกลายเป็นสำเร็จ)
- ประตูที่อ้างชื่อเครื่องมือแทน "สิ่งที่ต้องจริง" (D-P0-17) · เลขคำตัดสินเรียงชนกันสองสาย (ใช้เลขวันที่)
- แก้ไฟล์ live ตรง ๆ · deploy โดยไม่มียามที่แดงได้
- ยามที่ผ่านตลอด · ผู้เขียนตรวจงานตัวเอง
