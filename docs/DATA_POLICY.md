> **เขียนจากการเปิดตารางจริงเมื่อ 2026-08-29 ไม่ใช่จากความจำหรือจากเอกสารเก่า**

**สองสิ่งที่คลาวด์ไม่มี และมีตัวบังคับในฐานไม่ให้มีได้:**

1. **เนื้อข้อความของคน** — `inbox_event.body_ref TEXT CHECK (body_ref IS NULL)`
   เป็น constraint ระดับฐาน ⇒ **ต่อให้โค้ดพยายามเขียน ฐานจะปฏิเสธ** ไม่ใช่แค่ "เราตั้งใจไม่เขียน"
   วัดจริง: `SELECT COUNT(*) FROM inbox_event WHERE body_ref IS NOT NULL` = **0**
2. **พิกัด GPS ของคน** — ตาราง `task` มีคอลัมน์ `location_lat`/`location_lng` ติดมาตั้งแต่ schema แรก
   แต่ **ไม่มีโค้ดที่ไหนเขียนลงไปเลย** (grep ทั้ง `worker/src` ไม่พบจุดเขียน) และวัดของจริงได้ **0 แถว**
   ⚠ **นี่คือช่องที่เปิดค้างอยู่** — คอลัมน์ที่มีอยู่แต่ยังไม่มีใครใช้ คือคอลัมน์ที่วันหนึ่งจะมีคนใช้โดยไม่ได้ตั้งใจ
   ⇒ ต้องมีใบสั่งของมันเองว่าจะ **ลบคอลัมน์ทิ้ง** หรือ **ทำระบบ consent ก่อน** (ARCHITECTURE.md §3 ข้อ 1)

## 4. ถ้าพนักงานขอให้ลบข้อมูลของตัวเอง

### 4.1 ลำดับการลบ — ฝั่งคลาวด์ก่อนเสมอ

คลาวด์มี FK จริง ลบผิดลำดับจะติด `ON DELETE RESTRICT`:

```sql
-- 1) ตัดการผูกตัวตนก่อน (person_link -> person เป็น RESTRICT ⇒ ลบ person ก่อนไม่ได้)
DELETE FROM person_link WHERE person_code = :code;
-- 2) ledger เป็น ON DELETE SET NULL ⇒ ลบ person แล้ว actor_code กลายเป็น NULL เอง
--    เก็บแถวไว้โดยเจตนา: ledger คือหลักฐานว่าระบบส่ง/ไม่ส่งอะไรออกไป ไม่ใช่ข้อมูลของคน
-- 3) งานที่ยังอ้างถึงเขา — เปลี่ยนเป็นไม่มีเจ้าของ ไม่ใช่ลบทิ้ง (งานเป็นของบริษัท)
UPDATE task SET assignee_person_code = NULL WHERE assignee_person_code = :code;
UPDATE task SET creator_person_code  = NULL WHERE creator_person_code  = :code;
-- 4) ค่อยลบตัวคน
DELETE FROM person WHERE person_code = :code;
```

### 4.2 ลำดับการลบ — ฝั่ง LIVE

ไม่มี FK บังคับ ⇒ ลำดับเป็นเรื่องความถูกต้องเชิงตรรกะ ไม่ใช่เรื่องฐานยอมหรือไม่ยอม

```
1. ตัดทางเข้าก่อน   tbl_staff_remember · tbl_line_state · tbl_line_user   (กันเข้ามาระหว่างลบ)
2. ทะเบียน/สิทธิ์     tbl_line_directory · tbl_notify_sub · tbl_rolemaster
3. ของที่เป็นของเขาล้วน  tbl_attendance_claim · tbl_leave_request · tbl_tool_nudge_ack
4. ไฟล์บนดิสก์        uploads/attendance/*/<user_id>_*  ·  uploads/tasks/<id>/  (รูปที่เขาส่ง)
5. งาน/กิจกรรม        **ไม่ลบ** — เปลี่ยนผู้อ้างอิงเป็น NULL แทน (ดู 4.3)
6. tbl_user           ปิดบัญชี **ที่ `db_fim` ไม่ใช่ที่นี่** (ฝั่งนี้เป็นผู้อ่าน ไม่ใช่เจ้าของ)
```

> `tbl_task_photo` มี `File_Hash` แล้ว (WP-P4-A) ⇒ ตรวจได้ว่าไฟล์บนดิสก์ตรงกับที่บันทึกไว้ไหม
> ก่อนลบ — ไฟล์ที่ hash ไม่ตรงแปลว่ามีอะไรเปลี่ยนไประหว่างทาง ต้องรู้ก่อนลบ ไม่ใช่ลบทับ

### 4.3 สิ่งที่ระบบนี้ **ลบให้ไม่ได้** — ต้องบอกผู้ขอตรง ๆ

- **เวลาทำงานและวันลาที่ส่งบริษัทไปแล้ว** — ความจริงชุดนั้นเป็นของบริษัท ไม่ใช่ของระบบนี้
  (พนักงานเขียนกระดาษส่งเอง) ระบบนี้เป็นแค่ผู้ช่วยจำ ⇒ ลบของเราไม่ได้ทำให้ของบริษัทหายไป
- **งานที่เขาทำ** — เป็นบันทึกของบริษัทว่างานนั้นเกิดขึ้นจริง ⇒ ถอดชื่อออก (`NULL`) ไม่ใช่ลบใบงาน
- **`ledger` บนคลาวด์** — เป็นหลักฐานว่าระบบส่งอะไรออกไป จำเป็นต่อการตรวจสอบระบบเอง
  ⇒ ตัดความเชื่อมโยงกับตัวคน (`actor_code = NULL`) แต่แถวยังอยู่
- **`tbl_userlog`** — 458,663 แถวและมี IP · ลบเฉพาะรายคนได้ในทางเทคนิค
  แต่ **ยังไม่มีใครเคาะว่าควรลบหรือควรเก็บเป็นหลักฐานความปลอดภัย** ⇒ ต้องถามก่อน

### 4.4 ยังไม่มีอยู่จริง (อย่าสัญญากับใคร)

- ❌ **ไม่มีสคริปต์ลบอัตโนมัติ** — ลำดับข้างบนคือขั้นตอนที่คนต้องลงมือเอง
- ❌ **ไม่มีหน้า export ข้อมูลของตัวเอง** — ยังต้องให้ผู้ดูแลดึงจากฐานให้
- ❌ **ไม่มีระบบ consent** — ยังไม่มีที่ไหนที่พนักงานกดยอมรับ ⇒ **ยังแตะ GPS ไม่ได้** (§3 ข้อ 1)
- ❌ **ไม่มีบันทึกว่าใครเคยขอลบ/เคยลบอะไรไปแล้ว**
